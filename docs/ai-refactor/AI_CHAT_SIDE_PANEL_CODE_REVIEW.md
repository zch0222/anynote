## 1. 总体结论

**综合评分：72 / 100（中等偏上）。核心功能完成度较高，正常路径运行表现较好，但尚不满足“完整验收”条件。**

实现不是简单 Demo：六类资源、三类引用入口、桌面多标签、移动覆盖层、笔记编辑、刷新恢复、懒加载和真实栈 E2E 都已有实质成果，模块边界也大体符合方案。不过，本轮静态审查确认了 **3 个高优先级问题**，分别影响跨账号本地隔离和未保存笔记保护；另有新会话误持久化、恢复数据校验不足、测试矩阵缺口及首屏预算失败。

因此，当前状态更适合定义为：**功能已实现、可继续内部试用，但 M19.7 不应关闭；在共享设备、离线或保存失败场景下不宜按完全可靠功能交付。**

## 2. 实现得好的部分

- **资源覆盖完整。** `ResourceTarget`、六类 definition/body、正文编号、引用来源和过程区结果条目均已接入，不是只完成笔记单一类型。
- **正常路径的点击策略清晰。** 普通左键进入侧栏，修饰键和中键保留浏览器行为，PDF 问答页的 `onCitation` 优先逻辑仍保留。
- **状态模型具备真实功能。** 标签去重、导航版本、最近使用顺序、10 标签淘汰、关闭后激活、分区迁移和守卫均有实现与单测。
- **懒加载方向正确。** 首屏 provider 很轻，宿主、注册表和正文按需加载；PDF、视频与编辑器没有因为侧栏实现直接变成首屏静态依赖。
- **笔记没有另造保存引擎。** 侧栏复用 `useNoteEditorSession`、自动保存、冲突处理、协同组件和卸载补发，并增加新窗口前 `flush`、可见时同步外部版本。
- **桌面布局完成度较好。** 推入、临时收起会话列表、覆盖、最大化、拖拽与键盘调整均有纯函数和组件测试。
- **已有真实栈证据。** 留存的 Playwright 原始日志显示 16 passed / 6 skipped；6 条跳过均为桌面/移动项目分工，不是失败重试后隐藏。

## 3. 主要问题

### 高 1：登出与账号切换没有清空进程内侧栏状态，破坏按用户隔离

**证据链：**

- 侧栏分区保存在模块级 Zustand store 中：`apps/web/src/features/side-panel/store.ts:74-77`。
- 登出只清查询缓存和本地存储，随后 SPA 跳转登录页，没有重置该 store：`apps/web/src/features/auth/use-logout-mutation.ts:26-36`。
- 登录成功后同样是 SPA 导航：`apps/web/src/features/auth/components/login-form.tsx:47-50`。
- 持久化 hook 只有在“前一个用户 id 非空且直接变成另一个非空 id”时清 store：`apps/web/src/features/side-panel/persistence.ts:183-195`。宿主重新挂载后 `loadedFor` 又从 `null` 开始，无法满足这个条件。
- `hydrate` 遇到已有分区会跳过，而不是用新用户数据替换：`apps/web/src/features/side-panel/store.ts:337-345`。

**实际影响：**

A 用户登出、B 用户在同一浏览器页面会话中登录后，A 的 `surfaces`、内存标题提示和最近使用顺序仍可能留在 store 中；后续保存还可能把旧分区写入 B 用户的本地键。尤其是所有用户共用的 `chat:new` / `chat:new:kb<id>` 分区，在新对话页面更容易直接碰到旧标签。

这**不是后端权限绕过**，资源查询仍会使用 B 的权限；但它是明确的本地隐私与状态正确性问题，也违反方案 S7 的“按用户 id 隔离、登出清理”。

**建议：** 登出时同步重置侧栏内存；用户 id 变为 `null` 或发生任何变化时都应隔离旧状态。内存分区也应绑定用户，而不只是 localStorage 键带用户 id。补 A 打开侧栏 → 登出 → B 登录 → 新对话及已有对话的回归测试。

### 高 2：移动端浏览器返回会绕过守卫取消结果，仍然卸载笔记编辑器

`apps/web/src/features/side-panel/mobile/host.tsx:125-133` 的 `popstate` 处理依次调用：

1. `setOpen(surface, false)`；
2. 不检查实际 store 状态，直接 `onPanelOpenChange(false)`。

但 `setOpen` 在守卫返回 `false` 时会放弃状态修改：`apps/web/src/features/side-panel/store.ts:255-264`。此时 shell 仍被强制设为关闭，宿主又在 `apps/web/src/features/side-panel/mobile/host.tsx:182` 直接返回空，活动笔记编辑器随覆盖层卸载。

**实际影响：** 笔记处于离线、保存失败或冲突状态时，用户触发返回并在确认框选择“取消”，覆盖层仍会关闭，取消没有保护作用。卸载补发不能覆盖这些风险状态，可能丢失仅存于内存的修改。

**测试缺口：** `apps/web/src/features/side-panel/__tests__/mobile-host.test.tsx:20-62` 只测关闭按钮和 Esc，没有 `popstate`、守卫拒绝或历史状态恢复用例；既有 E2E 返回用例也没有先制造未保存风险。

**建议：** 只有 store 确认已经关闭后才能修改 shell；守卫拒绝时保持覆盖层，并处理已经 pop 掉的历史标记。补“返回 → 取消 → 仍在原标签且草稿保留”的组件与真实浏览器用例。

### 高 3：“打开完整页面”通过程序化导航绕开笔记离开保护

- 桌面笔记直接 `router.push(href)`：`apps/web/src/features/side-panel/tabs/note/body.tsx:142-145`。
- 移动端顶部菜单也直接 `router.push(href)`：`apps/web/src/features/side-panel/mobile/host.tsx:229-245`。
- `useLeaveGuard` 只拦截文档中的 `<a>` 点击和 `beforeunload`，覆盖不到按钮触发的 App Router 导航：`apps/web/src/features/notes/use-leave-guard.ts:21-62`。
- 笔记虽然登记了 `confirmLeave`，但它只被侧栏的切换、关闭和收起动作调用：`apps/web/src/features/side-panel/tabs/note/body.tsx:43-48`。

**实际影响：** 在离线、保存失败或冲突状态选择“打开完整页面”，不会出现方案要求的离开确认。SPA 卸载时的 `flushDetached("fetch")` 会在离线、冲突或不可重试失败等分支跳过补发，不能替代确认，相关实现见 `apps/web/src/features/notes/use-save-note.ts:450-465`。

**建议：** 将完整页面导航纳入同一个受守卫动作，确认通过后再导航；需要保留“先保存再进入历史/完整页面”的语义时，应复用现有会话能力。覆盖桌面、移动端及确认/取消两路测试。

### 中 1：新会话分区被写入持久化，违反“拿到会话 id 后才写”

`saveSidePanelState` 仅检查 `surfaceKey.startsWith("chat:")`：`apps/web/src/features/side-panel/persistence.ts:121-124`。因此 `chat:new` 和 `chat:new:kb3` 也会被写入，而方案 §5.6 明确要求只写 `chat:c<id>`。

**影响：** 新会话尚未创建成功就可能留下标签；再次进入新对话时可能恢复旧标签，占用 50 分区额度，并放大“高 1”的跨账号共用 key 问题。

**测试缺口：** `apps/web/src/features/side-panel/__tests__/persistence.test.ts:117-131` 只断言 `chat:c1` 会写、`pdf:doc:3` 不写，没有 `chat:new` 反例。

**建议：** 只接受严格的 `chat:c<正整数>` 分区，并考虑读取时清理此前已经写入的 `chat:new*` 数据。

### 中 2：持久化校验没有验证 `kind`，合法 JSON 仍可令宿主崩溃

资源标签 schema 只要求 `kind` 是非空字符串：`apps/web/src/features/side-panel/persistence.ts:38-42`。恢复时原样写入记录：`apps/web/src/features/side-panel/persistence.ts:234-250`；渲染时未注册的 `kind` 会直接抛错：`apps/web/src/features/side-panel/registry.ts:66-69`。

**影响：** 旧版本遗留、手工修改或局部损坏的 localStorage 只要其余字段符合 schema，就不会按方案“只删除该用户键并回到空状态”，而可能让右侧栏渲染失败。`kind` 与 `ref.type` 不一致也没有被拒绝。

**建议：** 恢复时校验注册类型、`kind` 与 `ref.type` 的一致性及标签 id 唯一性；补未知 `kind`、类型错配和重复 id 用例。

### 中 3：测试数量较多，但没有达到方案规定的分支与打桩层级

- `apps/web/src/features/side-panel/__tests__/tabs.test.tsx:4-46` 大量 mock 领域 hooks，而方案 M19.4 要求网络层打桩到 `openapi-fetch` 客户端。这能测组件分支，不能验证查询参数、拆包和错误分类的集成。
- 该文件只有 7 条用例，未导入或测试 `MoocTabBody`；慕课目录展开、子条目打开、加载/错误分支没有组件测试。
- 资料有较完整的不可读/重试测试，但其他类型并未逐项覆盖方案要求的加载、不可读、网络错误和重试矩阵。
- 移动宿主没有 `popstate` 单测，笔记正文没有“打开完整页面”的守卫测试，持久化 hook 没有账号切换测试。三个高优先级问题正好落在这些空白区。
- 协同构建下双端编辑、编辑器浮层、软键盘贴底仍只有“未验证”记录。

**评价：** 现有测试对正常路径有效，但不能用“全部通过”推导出方案验收矩阵已经完整。

### 中 4：新生产构建后首屏预算仍失败，且高于此前接受的超预算值

本轮执行新生产构建后，`/ai/chat` 与 `/ai/chat/[id]` 均为 **310.6 KB / 310.0 KB**；移动端最重路由 **247.3 / 250.0 KB** 通过，编辑器 chunk **18.0 / 250.0 KB** 通过。

方案记录此前用户接受的是 310.3 KB、超 0.3 KB；后续文档已指出 310.5 KB 需要重新确认。本轮新构建为 310.6 KB，因此不能把旧的 0.3 KB 接受记录当作当前门禁通过的依据。

**建议：** 按原方案继续压缩首屏，不自行上调预算；若产品决定接受当前体积，应明确记录新的接受值，同时仍保持“门禁未通过”的事实，不把豁免写成绿色结果。

### 低 1：完整页面地址仍有两份独立实现，核心“单一描述”被削弱

`citationHref` 在 `apps/web/src/lib/ai/citations.ts:54-94` 独立生成地址，`resourceHref` 又在 `apps/web/src/lib/ai/resource-target.ts:145-186` 生成一次。该偏差虽已在方案 §16 记录为首屏体积取舍，但长期维护风险真实存在。

两份测试主要分别断言硬编码字符串，并没有对同一组输入直接比较 `citationHref` 与 `resourceHref`；`apps/web/src/lib/ai/__tests__/resource-target.test.ts:17` 的“与旧引用实现逐字节一致”注释强于实际断言方式。

**建议：** 若暂时不能合并实现，至少增加同一输入的跨实现参数化等价测试，覆盖六类、两端、可选字段和非法定位。

### 低 2：删除会话的本地清理由懒加载宿主是否存在决定

`notifyConversationRemoved` 只调用可选处理器：`apps/web/src/features/side-panel/surface-events.ts:26-33`；没有挂载过宿主时处理器为 `null`。删除会话成功后的逻辑也只有这次通知：`apps/web/src/features/ai/use-conversations.ts:126-143`。

**影响：** 用户从未打开侧栏时，删除会话不会移除 localStorage 中对应分区；标识会留到后续淘汰或登出清理。

**建议：** 删除会话的持久化清理不应依赖 UI 是否挂载，并补“未挂载宿主时删除会话”的测试。

### 低 3：移动端 `tabpanel` 的 `aria-labelledby` 指向不存在的元素

`TabPanel` 总是设置 `aria-labelledby={labelledBy}`：`apps/web/src/features/side-panel/tab-panel.tsx:34-40`。但移动端 `MobileTitle` 和 `MobileTabPill` 没有设置对应的 `tabDomId`：`apps/web/src/features/side-panel/mobile/host.tsx:295-335`。

**影响：** 移动覆盖层中的正文面板缺少可靠的可访问名称；现有 Lighthouse 只检查未打开覆盖层的首屏，发现不了这个交互态问题。

**建议：** 给当前移动标题或标签按钮建立真实 id 对应关系，并补打开覆盖层后的无障碍检查。

### 低 4：注册表的部分扩展声明尚未真正接入容器

`TabDefinition` 声明了 `multiple`、`keepMounted` 和 `mobile`：`apps/web/src/features/side-panel/types.ts:68-95`，但当前行为分别是：

- `multiple` 由 `openPage` 调用方传参决定，而不是读取 definition：`apps/web/src/features/side-panel/store.ts:146-180`；
- `TabPanel` 只挂载活动正文，没有消费 `keepMounted`；
- 移动打开链没有消费 definition 的 `mobile` 标志。

当前六类定义都为移动端可用、也没有页面类正式消费方，所以这不是现阶段主流程故障；但它意味着方案所称“新增类型不改容器”尚未完全成立。

**建议：** 在开放外部扩展前，要么接通这些声明并补测试，要么从公开类型中移除尚未承诺的能力。

## 6. 建议的收尾顺序

1. **先守数据与隔离：** 修复账号切换内存清理、移动返回守卫、完整页面导航守卫，并用取消确认、离线/失败/冲突场景做回归。
2. **再收敛持久化：** 禁止 `chat:new*` 写入，强化恢复 schema，令会话删除不依赖宿主挂载。
3. **补齐真正缺失的测试：** 账号 A → B、`popstate` 守卫拒绝、完整页面取消离开、慕课目录及各资源异常分支；网络打桩层级按方案补齐。
4. **处理门禁与剩余环境验证：** 首屏回到 310 KB 内，或重新取得明确豁免；完成协同构建、编辑器浮层、移动软键盘及打开覆盖层后的无障碍验收。
5. **最后关闭 M19.7：** 在上述项完成前，建议保持“功能已实现、验收收尾中”，不要仅因正常路径 E2E 全绿而标记完整完成。

## 7. 最终评价

这份实现的主要价值在于，它已经搭出了可扩展右侧栏的大部分真实能力，而不是把几个详情页硬嵌进对话框；正常路径的桌面与移动体验也有真实栈证据支撑。主要短板不是代码量或模块数量，而是**失败路径没有与正常路径达到同等完成度**：离开保护有三个关键边界失守，持久化把“按用户隔离”落实到了磁盘键，却漏掉了进程内状态。

因此，本报告给出的结论是：**架构方向值得保留，功能基础较好；先修复高优先级可靠性问题，再进行一次以异常路径和账号隔离为重点的验收，之后才适合宣布方案完整落地。**
