## 1. 总体结论

**修复有实质效果，但还没有完整闭环，建议继续保持 M19.7 未关闭。**

首轮三个高优先级问题所指的具体路径——登出清空内存、移动返回取消、桌面/移动“打开完整页面”取消——均已有对应修复。持久化键、恢复数据校验、只读资源异常分支测试和移动可访问名称也明显改善。本轮运行的相关测试 **21 个文件 / 199 条全部通过**，类型检查和本批文件 Biome 检查通过。

不过，复核发现 **1 项高优先级遗漏、1 项中优先级残留，以及 1 项中优先级回归测试缺陷**：

1. 桌面切换会话、新建会话仍直接进行程序化导航，未保存笔记保护仍有旁路。
2. 宿主卸载后删除会话只清磁盘、不清内存；后续持久化可重新写入已删除分区。
3. 新增账号切换 E2E 在关键步骤使用整页导航，丢掉了它应当检验的进程内状态。

前两项已通过读取现有源码执行的临时内存探针确认，未向仓库写入复现代码；第三项由测试路径静态确认。这意味着“相关单测通过”和“历史 E2E 20 passed”都不能直接推导出全部风险已经关闭。

## 3. 本轮发现

### R2-01 · 高 / P1：桌面切换或新建会话仍绕过未保存笔记守卫

**性质：首轮漏检的同类问题，并非“打开完整页面”修复失效。**

代码链路：

- `apps/web/src/features/ai/components/conversation-list.tsx:103`：“新对话”按钮直接 `router.push("/ai/chat")`。
- 同文件 `:157`：切换会话直接 `router.push(...)`；实际点击元素在 `:230–234`，是 `<button>`。
- `apps/web/src/features/notes/use-leave-guard.ts:32–39`：捕获监听只处理 `<a href>`，遇到上述按钮直接返回。
- 新增的 `requestLeave` 只在侧栏内完整页面入口调用，没有接入这些会话动作。
- `apps/web/src/features/notes/use-save-note.ts:450–455`：卸载补发在 `blocked`、`halted` 或离线时直接返回，无法挽回这些情况下的草稿。

**触发方式：** 在会话列表可见的桌面宽度下，打开侧栏笔记，制造离线、不可重试保存失败或冲突，再点击另一会话或“新对话”。导航可以直接发生，原活动编辑器卸载，没有笔记离开确认。存于编辑器/保存 hook 内存中的改动可能丢失。

**本轮复现证据：** 在 jsdom 中加载实际 `ConversationList` 和 `useLeaveGuard` 源码，查询、UI 外壳和路由打桩，启用离开守卫并将 `window.confirm` 设为返回 `false`。分别点击另一会话与“新对话”，结果为：

```json
{
  "leaveGuardActive": true,
  "confirmReturns": false,
  "confirmCalls": 0,
  "routerPushCalls": ["/ai/chat/8", "/ai/chat"]
}
```

该探针确认了“守卫启用但按钮导航不询问”的路径；草稿丢失后果由编辑器卸载和 `flushDetached` 的失败分支静态确认，本轮未在真实浏览器制造丢失。

删除当前会话也需要一并检查：`conversation-list.tsx:69–77` 只确认删除对话，然后执行删除与导航；本次接通的 `store.ts:308–317` 会直接移除分区及守卫。删除聊天记录的确认不等于用户同意丢弃独立笔记中的改动。

**建议与验收：** 切换/新建会话统一先调用当前分区的离开守卫；删除当前会话时在实际删除请求之前完成草稿风险确认。以保存失败草稿覆盖“取消后地址、活动会话、编辑器和正文不变”，并覆盖允许离开分支。方案 §5.7 关于“切换会话都是站内链接”的假设也应在后续修复时订正。

### R2-02 · 中 / P2：宿主卸载后删除会话，已删除分区会被内存重新写回

**性质：首轮低 2 的修复不完整。影响本地状态清理，不会恢复已删除的服务端聊天记录，也不构成后端权限绕过。**

代码链路：

1. `apps/web/src/features/side-panel/surface-events.ts:14–23` 的处理器跟随宿主登记与卸载；卸载后 `removeHandler = null`，`:32` 的通知为空操作。
2. `apps/web/src/features/ai/use-conversations.ts:139–145` 新增的按需清理只调用 `removePersistedConversationSurface`。
3. `apps/web/src/features/side-panel/persisted-surfaces.ts:16–51` 只读写 localStorage，没有移除模块级 store 中的同名分区。
4. 同一用户重新挂载时，`persistence.ts:209–211` 不清空内存；`store.ts:344–352` 的 `hydrate` 是合并，磁盘中不再存在的分区也不会从内存删除。
5. 下一次侧栏变化触发 `persistence.ts:226–235`，重新序列化整个 `surfaces`，已删分区随之写回。

**真实可达的操作顺序：** 移动端打开会话 A 的侧栏 → 关闭覆盖层并返回 `/m/ai/chat` 列表（宿主卸载）→ 删除 A → 打开 B 的侧栏。桌面从其他页面回到未挂载侧栏的会话列表也有同类情况。

**本轮复现证据：** 临时 Node 进程转译并调用实际 store、surface-events、persistence 与 persisted-surfaces 源码，使用内存 localStorage 和静态资源注册表替身，模拟挂载/卸载、删除通知和下一次保存。输出：

```text
删除后：diskDeleted = true，memoryKeys = ["chat:c7"]
下一次分区变化并保存后：persistedKeys = ["chat:c8", "chat:c7"]
```

因此磁盘删除确实执行了，但没有持久地消除该分区。现有 `use-conversations.test.tsx` 只预置磁盘数据，没有预置“宿主曾经留下的内存状态”，覆盖不到这个分支。

**建议与验收：** 删除成功后的内存清理也应独立于宿主生命周期，可采用按需加载 store 或能覆盖宿主卸载期的删除事件机制；同时保证持久化最终状态不含被删会话。补“挂载过 → 卸载 → 删除 → 再挂载并产生保存”的用例，断言内存和磁盘始终都没有 A。

### R2-03 · 中 / P2：账号切换 E2E 在验证前重建文档，无法检验原内存残留

**性质：新增回归用例未保留原缺陷的前提；不据此否定已经实现的账号隔离修复。**

`apps/web/e2e/support/agent-retrieval.ts:655–700` 的用例声称检查同一页面会话内的跨账号内存隔离，但关键步骤是：

- A 打开侧栏后，`:667` 用 `page.goto("/m/me")` 进入登出页；这是整页导航，旧文档中的模块级 Zustand 状态已经被销毁。
- B 登录后，`:695` 又用 `page.goto(conversationUrl)` 重建文档，再检查侧栏没有标签。

该用例能证明重载后的显示结果，**不能证明同一个 JavaScript 文档里的 A 用户内存已被清理**，也无法可靠防止首轮高 1 的缺陷重新引入。它只检查 A 的已有会话，没有覆盖首轮特别指出的 `chat:new` 共用分区。

现有 `persistence-hook.test.ts` 的两个用例覆盖同一 hook 实例的 A→B 和 A→空值；登出单测覆盖事件重置。它们仍有价值，但没有直接覆盖“卸载 A 宿主，再挂载 B 宿主”的新增模块级身份逻辑。

**建议与验收：** 保持同一 document，通过 SPA 入口完成侧栏 → 登出 → 登录 → 新对话/已有对话的全过程；设置文档内哨兵并断言未重载，随后断言 A 的标签和提示不在 B 的 store/界面中，也不会写入 B 的存储键。补持久化 hook 的卸载/重挂载测试。本轮未回退修复代码执行该 E2E，结论来自测试路径审查。

## 4. 修复质量与证据上的其他限制

### 4.1 完整页面守卫 E2E 证明了处理器分支，未完整证明菜单可操作

`apps/web/e2e/support/agent-retrieval.ts:202–226` 的 `clickPanelMenuItem` 用 `page.evaluate`、`MutationObserver` 和 DOM `click()`，在菜单项出现时立即触发；注释明确说明这是为了绕开保存状态更新导致菜单关闭。

这仍能覆盖点击处理器及确认取消逻辑，但绕过了 Playwright 的可见、稳定、可接收指针事件等检查。不能以这两条 E2E 证明真实用户能稳定打开菜单并选中条目。现有“保存失败时更多菜单可用”单测使用固定的 session 替身，也未模拟状态持续变化。

建议后续用普通 locator 点击验证菜单在保存状态变化期间仍可操作。这里记录的是证据不足，本轮没有据此直接认定真实菜单一定存在故障。

### 4.2 E2E 清理成功不能由测试通过数推导

同文件 `:237–251` 将夹具删除失败全部吞掉；新账号切换用例会撤销默认会话，清理是否完成没有断言。`tmp/m19-side-panel/e2e-report.json` 中 `playwrightPassed=true`，但 `harnessConfigRestored=false`、`harnessPrefetchRestored=false`。

修复清单将后两项解释为比较口径，并记载人工确认了 `prefetch-enabled=false`。本轮未访问 Nacos，也未核对夹具最终是否删除，因此只认定“测试日志通过”，不扩大为“所有运行配置与夹具均已确认恢复”。建议将后续清理结果明确输出，避免无日志的失败影响复跑。

### 4.3 已知例外与未验证项应继续保留

- **首屏预算：** 已有明确接受 310.7 KB 的记录，本轮无需重新请求豁免；预算值仍为 310.0 KB，命令退出码仍为 1。
- **扩展字段：** `keepMounted` 的未实现已在注释中明示；当前功能可继续使用，开放相关扩展前应实现或移除该能力声明。
- **真实环境：** 协同构建下双端编辑、编辑器浮层层级、移动软键盘与真实设备仍未验证。本轮也未做新的视觉、Lighthouse 或屏幕阅读器验收。
