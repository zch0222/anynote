## 第三轮补充发现与处理优先级

### 发现一　P2　删除 A 的迟到响应会把用户从会话 B 带走

上一轮记录的是用户点击按钮时没有询问草稿。本项需要在删除 A 的请求完成前已经进入 B，直接影响是意外跳转。要进一步丢稿，还需要 B 当时有未保存改动且卸载补发失败。初稿把潜在丢稿列为 P1，高估了现有证据支持的紧迫性。

在会话 A 确认删除，暂缓 DELETE 响应，随后通过列表正常进入 B。删除期间禁用的是行操作菜单，打开其他会话的按钮仍可用。A 的异步回调在 `await` 之后继续比较点击时捕获的 `activeId`。即使 A 的列表已卸载，条件仍成立，因而调用 `router.replace("/ai/chat")`。[删除回调](../../apps/web/src/features/ai/components/conversation-list.tsx#L83) · [会话按钮与禁用范围](../../apps/web/src/features/ai/components/conversation-list.tsx#L245)

本轮在 jsdom 中点击 A 的删除菜单，保留待完成的请求，点击进入 B，卸载 A 的列表并挂载 B 的列表。给 B 登记拒绝离开的守卫，随后完成 A 的请求。路由替身收到一次 `replace("/ai/chat")`，B 的守卫调用次数为 **0**。若此时 B 有保存失败或离线的笔记草稿，卸载补发可能直接返回，存在丢稿风险。探针观测到的是跳转调用与守卫旁路，未在真实浏览器中丢弃用户正文。[卸载时的保存条件](../../apps/web/src/features/notes/use-save-note.ts#L450)

验收时应保留“停在 A、删除成功后回到新对话”的行为。延迟同一请求并先进入 B 后，A 的删除只能清理 A。B 的地址、编辑器和失败草稿应完整保留。

### 发现二　P3　磁盘清理完成前重新挂载，会把已删侧栏分区写回

第二轮已记录“删除 A 后打开 B，后续保存又写回 A”这一用户操作和结果。本轮新增的前提是同账号宿主恰在磁盘旧值尚未清除时重新挂载。常规顺序已通过回归，剩余影响限于浏览器中的侧栏标识，建议低优先跟踪。[第二轮复现步骤](./AI_CHAT_SIDE_PANEL_CODE_REVIEW_ROUND_2.md#L100)

删除成功后先同步通知内存移除，再通过 `void import(...)` 启动本地存储清理。删除操作可以先向调用方报告成功。现有生产构建也把清理函数放在单独的 5931 号 JS 文件中。此时重新挂载宿主，持久化 hook 会读到磁盘旧值并合并回内存。迟到的清理只改磁盘，下次防抖保存又把内存里的旧分区写回。[删除成功回调](../../apps/web/src/features/ai/use-conversations.ts#L138) · [重新挂载与防抖保存](../../apps/web/src/features/side-panel/persistence.ts#L208) · [磁盘清理](../../apps/web/src/features/side-panel/persisted-surfaces.ts#L16)

本轮使用真实删除 hook、store、恢复和保存函数，仅延迟清理模块加载，并为后端返回成功。删除 `chat:c7` 后内存立即移除了它。在模块就绪前重挂载，内存恢复 `chat:c7`。放行清理并确认磁盘已移除它，再收起 `chat:c8`，等待实际防抖写入。最终磁盘分区为 **`["chat:c8", "chat:c7"]`**。影响是旧标签和资源标识重新出现在本地侧栏状态，服务端会话的删除仍然有效。

现有回归先等待磁盘清理才重挂载。末次断言检查的 `c8 存在、c7 缺失` 在防抖写盘前就已成立。**关闭条件**是允许清理与重挂载交错，等到 `c8.open` 的新值确实写入后，再断言内存与磁盘均不含 `c7`。[现有回归的等待顺序](../../apps/web/src/features/ai/__tests__/use-conversations.test.tsx#L229)

### 发现三　P2　切换知识库后，迟到的 PDF 上传会覆盖新库选中的文档

PDF 切库是同批追加修复，第二轮报告未列出上传期间切库的情形。用户在上传 A 的文件期间切到 B，就可能看到 B 的列表配上 A 的文档。在 B 另选文件只为验证明确的选择会被覆盖。上传可能持续一段时间，操作无需精确卡在某一瞬间，建议按普通功能缺陷跟踪。

在知识库 A 开始上传 PDF，上传期间切到 B 并选择 B 的文档。A 的上传与建索引请求完成后，页面无条件调用 `setDocId(createdId)`。左侧列表继续按 B 查询，预览和问答则按 A 刚上传的文档 ID 工作。[上传完成回调](../../apps/web/src/features/ai/components/pdf/pdf-page.tsx#L159) · [列表与详情查询](../../apps/web/src/features/ai/components/pdf/pdf-page.tsx#L115) · [问答目标](../../apps/web/src/features/ai/components/pdf/pdf-page.tsx#L396)

本轮使用实际 PDF 页面，暂停 A 的上传响应，点选 B 和文档 202，再让 A 返回文档 101。选择器仍显示 B，列表查询仍取库 2，详情查询却从 **202 变成 101**。探针使用模拟上传和查询，未发起真实上传或模型请求。**关闭条件**是在相同顺序下，A 的上传可以完成，B 的列表、预览和后续问答仍指向用户最后选择的文档 202。
