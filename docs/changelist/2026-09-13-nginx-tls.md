# 2026-09-13 本机 Nginx 上 TLS：内网入口切 HTTPS（修复图片上传）

## 概览

把本机局域网入口从明文 HTTP 切到 **HTTPS（自签名证书）**，解决笔记图片上传
「粘贴 / 工具栏上传都失败、且根本没发出请求」的问题。根因是明文 HTTP 的内网 IP
**不是 secure context**，`crypto.subtle` 为 `undefined`，前端算 SHA-256 时直接抛
`Cannot read properties of undefined (reading 'digest')`——异常发生在第一个网络请求
**之前**，所以表现为"没有发请求"。

**这次没有改任何应用代码**，是刻意的：问题的性质是"运行环境不满足 WebCrypto 的

贴合设计意图，也顺带修好了同根因的另两条链路。

| 项 | 状态 | 作用与原因 |
|------|------|------|
| `sys_config.MIN_IO_CONFIG.publicEndPoint` | 修改 | `http://localhost:9000` → `https://192.168.3.90:9000`。两个理由：预签名 URL 的 **Host 计入 SigV4 签名**，浏览器请求的 Host 必须与签名时一致；且页面在 https 下时浏览器会拦掉指向 `http://` 的**混合内容**，分片 PUT 会被直接 block。 |

| web 镜像 | 重建 | `NEXT_PUBLIC_*` 是**构建时内联**，改来源后不重建镜像不会生效（容器启动即被 `config.mjs` 拦下）。 |

## 审计要点

1. **这是环境修复，不是代码修复**。`apps/web` 一行未改——`crypto.subtle.digest` 是标准
   Web API，写法本身没问题，缺的只是 secure context。因此评审重点在**配置一致性**，
   而不是代码逻辑。
2. **三个来源必须同时改，漏一个就整体不可用**：`NEXT_PUBLIC_APP_URL`（构建 + 运行时，
   被 `config.mjs` 逐字比对）、`NEXT_PUBLIC_COLLAB_WS_URL`（同上，且校验必须是同源
   `wss://.../collab`）、`COLLAB_ALLOWED_ORIGINS`（collab 侧精确匹配）。
3. **`:9000` 那个 server 也必须上 TLS**，容易被误认为「MinIO 是后端的事」而漏掉。
   页面在 https 下时，指向 `http://192.168.3.90:9000` 的分片 PUT 会被浏览器当作
   混合内容拦掉，图片上传依旧失败。
4. **`proxy_set_header Host $http_host` 在两个 server 里都不能动**。SigV4 把 Host 计入
   签名，改写即 `SignatureDoesNotMatch`；nginx 终止 TLS、回源用 http 是安全的
   （canonical request 不含 scheme）。
5. **刻意未开 HSTS 与 OCSP stapling**：本机需要在 https / http 之间来回切，HSTS 会让
   浏览器长期锁死 https；自签名 CA 没有 OCSP responder，stapling 只会一直失败。生产模板
   （`infra/nginx/nginx.conf`）不使用本机这套证书，不受影响。
6. **根 CA 私钥未保留**。签完 `server.crt` 后 `ca.key` 即删除，`conf/certs/` 只留
   `ca.crt`（公开信息）与服务器证书 / 私钥，缩小泄露面；重新签发按 `certs/README.md`
   从零走一遍即可。
7. **`http://localhost:3000` 不再是可用入口**。Nginx 只在 `192.168.3.90` 上监听 TLS，
   `127.0.0.1:3000` 是 Next 容器的明文端口，直连它仍是非 secure context。这一点写进了
   `certs/README.md` 的「已知限制」。

## 验证结果

全部为**实际执行过**的命令与真实输出。

| 命令 | 结果 |
|------|------|
| `openssl x509 -in server.crt -noout -ext subjectAltName` | `DNS:localhost, DNS:R9000P, IP Address:127.0.0.1, IP Address:192.168.3.90` |
| `openssl verify -CAfile ca.crt server.crt` | `server.crt: OK` |
| 私钥 / 证书 modulus 比对 | `MATCH` |
| `nginx -t` | `syntax is ok` / `test is successful` |
| `openssl s_client -connect 192.168.3.90:3000`（带 `-CAfile`） | `Protocol: TLSv1.3`、`Verify return code: 0 (ok)`、CN/issuer 正确 |
| `openssl s_client -connect 192.168.3.90:9000`（带 `-CAfile`） | 同上，TLSv1.3 + verify ok |
| `curl --ssl-no-revoke --cacert ca.crt https://192.168.3.90:3000/login` | `HTTP=200 verify=0` |
| `curl -k https://192.168.3.90:9000/anynote/` | `HTTP=403` + S3 风格 `<Error><Code>AccessDenied</Code>...<BucketName>anynote</BucketName>`——证明请求**确实到了 MinIO** 而非被 nginx 的 `location /` 拦成 404 |
| `curl https://192.168.3.90:9000/minio/health/live` | `HTTP=200` |
| BFF Origin 门禁（POST `/api/auth/login`） | 带 `Origin: https://192.168.3.90:3000` → `HTTP 400` + `{"code":"A0160","msg":"请求体必须是有效 JSON"}`（**已穿过 Origin 校验**，仅因探针体不合法被参数校验挡下）；带旧 `Origin: http://...` → `HTTP 403` + `A0301 请求来源不受信任`（反证门禁生效） |
| 容器环境核对（`printenv` / `cat web-build-config.json`） | 两者均为 `https://192.168.3.90:3000` 与 `wss://192.168.3.90:3000/collab`，容器启动通过 `config.mjs` 一致性校验 |
| 真实 Chromium 探针（`https://192.168.3.90:3000`） | `isSecureContext:true`、`hasSubtle:true`、`randomUUID:true`，且 `SHA-256("abc")` = `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad`（**与标准值逐字符相等**，证明 digest 真算对而不只是函数存在），控制台 0 报错 |
| `E2E_BASE_URL=https://192.168.3.90:3000 npx playwright test --project=chromium` | **23 passed / 0 failed**（改造前同样的命令在 http LAN 下是 4 条失败：图片 ×2、协同 ×1、PDF ×1） |
| 同上，`notes-image-upload.spec.ts` 单独跑 | **2 passed**——正是原先报 `crypto.subtle` 未定义的两条 |
| 同上，`collab.spec.ts` 单独跑 | **2 passed**——含 `crypto.randomUUID()` 建文档与双端同步 |
| 同上，`pdf-upload.spec.ts` 单独跑 | **3 passed** |
| 同上，`--project=mobile` | **27 passed / 1 failed / 2 did not run**。唯一失败是 `mobile-core.spec.ts` 的「返回列表再进来内容还在」——断言收到 `about:blank`，即移动端返回键 `router.back()` 在无站内历史时退到空白页。**与本次改动无关**：上一批 changelist（`2026-09-13-web-lan-origin.md` 失败归因表末行）已在纯 HTTP 下记录过同一条同因失败，属未修的既有缺陷。 |
| 整体对比（上一批 changelist 记录 vs 本次） | 纯 HTTP 下 `E2E_BASE_URL=http://192.168.3.90:3000` 全量是 **45 passed / 5 failed**（图片 ×2、协同 ×1、PDF ×1 为 secure context，移动导航 ×1 为既有缺陷）；本次 HTTPS 下桌面 23/23 全绿，5 条 secure-context 失败全部消除，只剩那条与 Origin 无关的移动导航用例。 |

> **改密码式的坑**：`docker compose` 的 `--env-file=/dev/null` 是 bash 写法，在 PowerShell
> 下会被解析成 `C:\dev\null` 并报 `couldn't find env file`。本次改用真实空文件
> `--env-file="$env:TEMP\anynote-empty.env"`，渲染结果与预期一致。
