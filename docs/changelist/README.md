# Changelist 编写规范

本目录存放**改动清单（changelist）**：一次成规模改动的逐文件说明，**供人在评审 / 审计时快速把握全貌**，
而不是替代 `git log` 或 diff 本身。

## 命名规则

```
docs/changelist/YYYY-MM-DD-<kebab-slug>.md
```

- 日期是**该批改动完成的日期**，不是文件创建日期。
- slug 用短横线小写英文，描述改动主题（`cli-frontend`、`gateway-bearer-only`），不要用 `update`、`misc` 这类空词。
- 与 `.claude/openspec/changes/` 的命名保持一致，两者经常互相引用。
- 同一天多批改动就用不同 slug，不加序号。

例：`2026-09-12-cli-frontend.md`

## 强制要求

1. **严格按 `git` 的实际结果编写，不允许凭记忆罗列。**
   开写前先执行并以输出为准：

   ```bash
   git status --porcelain | sort          # 未提交的改动
   git diff --stat                        # 已跟踪文件的增删行数
   git diff --stat <base>...HEAD          # 已提交到分支上的改动
   git ls-files --others --exclude-standard   # 新增（未跟踪）文件
   ```

   文件路径、增删行数、文件数量都要与命令输出对得上。写完再跑一遍复核。

2. **表格形式**，每行一个文件，至少三列：`文件` / `状态`（新增·修改·删除）/ `作用与原因`。

3. **一个文件一句话**，同时说清"做什么"和"为什么"。只写"新增 xxx 工具类"不合格——
   要写清它解决的问题（例："后端 `@Url` 切面拿 cover 做白名单校验，缺省会 NPE，所以这里先读再回填"）。

4. **按模块分章节**，一个章节一个包 / 服务 / 顶层目录，章节顺序从"影响面最大"到"最外围"。
   章节前可加一句话说明这块改了什么。

5. **简洁准确**。这是审计材料不是教程：不贴代码、不展开设计推导（那些进方案文档），
   一眼扫过去能判断"哪些文件需要重点看"。

6. **生成物必须标注**，并说明它由什么命令产出、是否被 CI 卡 diff，提醒评审看源头而不是产物。

## 必备章节

| 章节 | 内容 |
|------|------|
| 概览 | 新增 / 修改 / 删除文件数与行数、按目录的分布；**验证结果表**（跑过哪些命令、结果如何） |
| 各模块章节 | 逐文件表格，见上方要求 |
| 审计要点 | 3-6 条"最该重点看的地方"，说明看它的理由（易错、涉及安全、行为变更等） |

验证结果只写**实际执行过**的命令与真实输出；没跑的不要写，跑失败的如实写。

## 与其它文档的分工

| 文档 | 职责 |
|------|------|
| 本目录的 changelist | **这次改了哪些文件、为什么**，供人工审计 |
| `.claude/openspec/changes/` | **API / 契约层面的变更提案**，含背景、已确认契约、验证计划 |
| `docs/<主题>/*_PLAN.md` | 技术方案与设计取舍 |
| `docs/<主题>/*_MILESTONES.md` | 执行进度、与方案的偏差、验收记录 |
| `git log` | 变更的时间线与原子单元 |

changelist 不重复方案文档的内容，需要展开时用链接指过去。

## 归档

改动合并后 changelist **保留不删**，它是当时改动面的快照。
后续改动写新文件，不要回头改旧的（除非旧文件里的路径因重命名而失效，此时只改路径并注明）。
