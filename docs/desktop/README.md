## 这是什么

重新设计的桌面客户端，加上知识库新增的「Git 仓库」模块。三条核心判断：

1. **重做而不是接着做 `apps/desktop`**。现在的 Tauri 骨架只是一个打开远端网页的窗口，和浏览器没有区别，
   Rust 代码也从未编译过（[DESKTOP_PLAN §2.1](./DESKTOP_PLAN.md#21-现有-appsdesktop-只是远端网页的外壳)）。
   新客户端把界面打包进安装包，数据面直连网关（与 CLI 同口径），本地文件和 git 都在本机执行。
2. **只做两件事**：云端知识库里笔记的读写保存；本地 Markdown 文件像 Typora 一样编辑，并用 Git 管理。
   协同、AI、慕课、任务、资料（PDF）、成员管理都不做。
3. **git 只在桌面端跑**。知识库的「Git 仓库」模块在服务端只记绑定、游标和映射，不连仓库、不存仓库凭据；
   同步、合并、冲突处理都在桌面端完成，网页端只看状态和管理绑定。

## 背景：2026-10-01 的调研结论

| 结论 | 对方案的影响 |
|------|------|
| 现有编辑器保存会整篇重排：19 种常见写法里 15 种被改写，front matter / HTML / 脚注会被**破坏** | 本地文件编辑和 Git 同步都以「编辑器保真」为前置（M15.1）|
| 「按顶层块保留原文」的原型已验证：不编辑直接保存逐字节一致，改一段只差一段，撤销后又一致 | 保真方案的第一层可以直接落地，且不改 schema |
| Typora（0.9.98 源码）其实也不保留原文，每次保存整篇重新生成，靠「行内存 Markdown 原文 + 块级写法记在节点属性上」显得没改；它的已知缺陷（改一格整表重排、改一项整个列表插空行）都出在属性没覆盖到的地方 | 取它块级的做法，再加 Typora 没有的「原文兜底」（[DESKTOP_PLAN §6.9](./DESKTOP_PLAN.md#69-编辑器typora-式编辑与保真保存)）|
| 笔记权限创建时写死 `70000`：同一知识库的其他成员读不到彼此的笔记 | Git 同步只能代表一个人，先按「个人知识库」定位（[GIT_MODULE_PLAN §9](./GIT_MODULE_PLAN.md#9-权限与安全)）|
| CLI 的浏览器授权登录（回环 + PKCE）已上线，正是 RFC 8252 给原生应用设计的流程 | 桌面端直接复用，不新造登录协议 |

## 范围

**做**：

- 云端知识库：列表、新建、改名、删除；笔记新建、编辑、自动保存、改名、移动、删除、图片
- 本地仓库：打开文件夹、克隆远程仓库、文件树、Typora 式编辑、保存不重排、图片存到本地
- Git：状态、差异、提交、拉取、推送、克隆、历史、分支切换、合并冲突处理
- 知识库 Git 模块：绑定远程或本地仓库、双向同步、冲突处理、网页端状态 Tab

**不做**（理由见 [DESKTOP_PLAN §1.2](./DESKTOP_PLAN.md#12-非目标)、[GIT_MODULE_PLAN §1.2](./GIT_MODULE_PLAN.md#12-非目标)）：
协同编辑、AI、慕课、任务、资料（PDF）、成员管理、云端笔记历史页、离线编辑云端知识库、移动端、
服务端执行 git、服务端保存仓库凭据。

## 待拍板的决策

| # | 决策 | 推荐 | 备选 | 依据 |
|---|------|------|------|------|
| D1 | 桌面框架 | **Electron** | Tauri 2（现骨架） | 主进程用 TS，可复用 CLI 登录代码与 editor-core；三平台同一个 Chromium，与 web E2E 一致；本机不用装 Rust。代价是安装包大（[DESKTOP_PLAN §4.1](./DESKTOP_PLAN.md#41-electron-还是-taurid1)）|
| D2 | 「文档保存」的范围 | **笔记**（知识库里的文档）的读写保存；「资料」Tab 的 PDF 不做 | 资料列表只读 | 资料是给 AI 问答用的，属于不做的 AI 范围 |
| D3 | git 怎么执行 | **调用系统 git（≥ 2.30）**，没装就引导安装 | 内置 MinGit；libgit2 | 尊重用户已有的凭据助手、SSH 配置、钩子、LFS（[DESKTOP_PLAN §6.8](./DESKTOP_PLAN.md#68-git-基础能力)）|
| D4 | 已绑定 Git 的知识库在桌面端怎么编辑 | **本机有克隆时编辑本地文件**（可离线），同步时再和知识库对齐 | 永远在线编辑知识库，仓库只做镜像 | 与「像 Typora 一样编辑本地笔记」是同一条路径 |
| D5 | 同步方向的交付顺序 | **先「仅导出」，再「仅导入」，最后「双向」并设为默认** | 一步到位双向 | 双向依赖编辑器保真全部落地，分步交付风险小 |
| D6 | 多成员知识库 | **同步身份只有绑定者一人**；他看不到的笔记不进仓库 | 先修笔记权限模型再做 Git 模块 | 笔记权限缺口是既有问题，单独立项 |
| D7 | 图片进不进仓库 | **进**：同步时下载到 `assets/`，链接改相对路径 | 仓库里保留服务器地址 | 仓库要能脱离服务器单独阅读 |
| D8 | 编辑器保真完成前，网页端能否编辑已绑定的笔记 | **只读** | 允许（会产生整篇 diff）| 网页改一个字不能让仓库多出整篇 diff |
| D9 | 新建笔记的标题长度 | **后端放宽到 1–80**，与编辑接口一致 | 桌面端截断或补齐 | 文件名常短于 3 字或长于 15 字 |
| D10 | `apps/desktop` 怎么处置 | **原地重做**，Tauri 骨架与「令牌交换」链路一起退役 | 新目录并存 | 旧骨架沉没成本约为零，交换端点没有调用方 |
| D11 | 首发平台 | **Windows**，macOS / Linux 随后 | 三平台同发 | 开发与验收都在 Windows；macOS 需签名与公证 |

拍板结果回写本表和 [DESKTOP_MILESTONES.md](./DESKTOP_MILESTONES.md) 的 M15.0。
